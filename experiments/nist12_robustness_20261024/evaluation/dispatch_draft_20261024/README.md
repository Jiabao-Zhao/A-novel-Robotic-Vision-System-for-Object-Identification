# Isolated dynamic dispatch draft

This module is not imported by any running experiment. It only schedules supplied callables through supplied executors; it loads no CAD, GPU, model, data or labels. Root authorized new draft source and CPU-only fake-future tests, not integration or another fit.

`dispatch_unique_jobs` uses one shared unique-key iterator, CPU slots exactly2 or4, and one GPU slot. The caller must supply distinct spawn executors configured with those worker limits. The central dispatch body is27 lines excluding its two-line signature. Helpers handle validation, completion and an explicit failure report; this is not a complete GPU execution adapter.

The first slot is GPU, and freed slots take the next job. There are at most CPUslots+1 known futures and one GPU future. A validated matching result reaches `on_complete(key, backend)` once; the callback should verify the committed summary/bank and perform existing progress/scene bookkeeping. A callback exception is not retried or marked complete.

An ordinary Python `Exception` from a worker, result-key check, callback, submit or wait stops further assignment and drains all known accepted futures. Valid in-flight results still receive their callback once. `DispatchFailure.report` lists unsubmitted and unresolved keys; these are scheduling states, never fabricated unavailable scores. `assigned_keys` records attempted assignments, including a submit attempt that raised before returning a future; that key is unresolved, rather than unsubmitted. A failed callback may follow a valid scientific commit, so inspect normal cache evidence before any resume.

The caller owns executor shutdown and must verify worker exit/no remaining writer before retrying anything. In particular, an exceptional `submit` with ambiguous acceptance requires full executor shutdown and cache review; the draft cannot drain a future the executor never returned. Control interrupts such as `KeyboardInterrupt` and process termination require a separate integration policy; the tested contract covers ordinary exceptions, without trapping user cancellation through a broad `BaseException` handler. No automatic retries occur. It assumes a single serial cohort dispatcher and preserves the pilot/reservation handoff; it is not a cross-process filesystem lock.

Separate approval gates remain: successful current pilot; representative host capacity, especially above2M voxels; reviewed per-job GPU helper/lifecycle and bare-tree restoration; source/input/build/FP/ownership/commit guards; physical reserve admission; complete resource provenance and final prediction-lock coverage. Prefer closing a fresh GPU runtime before each original summary commit initially. Persistent Python CAD caches require lifetime memory accounting, and cached CADs must be rewrapped at each job even when their factory is not called. Ordinary all-CPU query banks below the GPU threshold must not inherit the dense pilot's mandatory positive-GPU assertion without an explicit policy.

The current pilot's pinned sources and outputs are unchanged. All original full searches remain required; the unanswered decision-only preference is unrelated to exact query acceleration.
